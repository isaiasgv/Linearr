Brand Identity

Voice & Tone

Four starter attributes to tune after a brand workshop — they govern every word Linearr writes, from marketing copy to error messages.

Starter Voice Attributes

Clear
Plain language over jargon. Say "delete" not "deprecate this record."
Confident
State what the product does. "Exports your report" — not "can help export."
Human
Talk to a person, not a role. Warm, real, never condescending.
Concise
Short sentences, active voice. Cut every word that doesn't earn its place.

In Practice

✓ Do
Clear, active, specific — "Publish" then "Published." Address the error, then the fix: "Couldn't save. Check your connection and try again."
✕ Don't
System-speak ("webhook config failed"), vague apologies ("Oops, something went wrong"), or exclamation-heavy copy.

Layout Anti-Patterns

✓ Correct
  • ✓All layout uses Tailwind spacing utilities (p-4, gap-6…) — never raw pixel values
  • ✓Max 4 stat cards per row — group additional metrics below
  • ✓Use minmax(0, 1fr) in CSS grid to prevent overflow
  • ✓Test every layout at 768px — a primary breakpoint for tablet users
✕ Avoid
  • ✕Nesting grids more than 2 levels deep
  • ✕Using position: absolute for layout — only for decorative overlays
  • ✕Hardcoding column widths in px — always use fractions or %
  • ✕More than 6 columns in a single row — always too dense at any width

Motion & Animation

Purposeful motion reinforces the product — fast, confident, efficient. Every transition should feel earned, not decorative.

Duration & Easing Tokens

TokenValueUse case
--duration-fast150msButton hover/active, badge appear, tooltip show
--duration200msPanel expand, dropdown open, tab switch, page fade
--ease-quietcubic-bezier(0.4, 0, 0.2, 1)The system default — every UI transition

Need a distinct entrance/exit feel? Layer standard CSS keywords (ease-out entering, ease-in leaving) on top of these two tokens — don't invent a new custom property for a one-off.

Motion Rules

  • ✓Always respect prefers-reduced-motion — remove all transitions when set
  • ✓Use transform and opacity only — GPU-accelerated, no layout reflow
  • ✓Keep exits faster than entrances — users don't need to watch things leave
  • ✕Never animate width, height, or top/left — causes layout reflow
  • ✕Never use motion longer than 500ms on an interactive element

CSS Tokens

CSS
--duration-fast: 150ms;
--duration:      200ms;
--ease-quiet:   cubic-bezier(0.4, 0, 0.2, 1);

@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    transition-duration: 0.01ms !important;
  }
}

Accessibility

  • ✓Always use <button> — never a styled <div> or <span>
  • ✓Icon-only buttons MUST have an aria-label
  • ✓Disabled: use the disabled attribute AND aria-disabled="true"
  • ✓Loading state: add aria-busy="true" plus visible text ("Saving…") — never a spinner alone
  • ✓Focus ring: :focus-visible with the shared --ring outline

Do's & Don'ts

✓ Do
Use one primary action per screen section. Pair it with a secondary or ghost button for cancel. Use imperative verbs: "Save", "Confirm", "Delete".
✕ Don't
Never stack two primary buttons. Never use a <div> with a click handler instead of a button. Never use "Click here" as a label — it fails WCAG 2.4.6.

Charts

Charts wrap a lightweight primitive with a token-disciplined API. Consumers never pass raw colors — only token names. The wrapping layer enforces brand and accessibility rules so individual chart usage stays simple, consistent, and bundle-efficient.

Philosophy

  • ✓Token-only colors. No fill="#2a78d6" — only highlightColor="primary" or series={1}. The wrapper resolves the CSS variable at runtime.
  • ✓No gradients. Outliers are highlighted with a different flat solid color — never a gradient fill or glow.
  • ✓Semantic meaning only. Color encodes data semantics (positive delta, highlighted outlier, category). Never decorative.
  • ✓Accessibility first. Every chart has role="img" plus a required ariaLabel. Tooltips use tabular-nums. Animations respect prefers-reduced-motion.
  • ✓Tight bundle. Each chart is tree-shakeable — budget ≤ 80 KB gzipped per page.

Accessibility

Accessibility

Accessibility is built into every token, component, and pattern — WCAG 2.2 Level AA is the non-negotiable baseline. Use this page as the final gate before shipping any screen.

✓
Accessibility wins over aesthetics

If a design decision conflicts with accessibility, accessibility always wins. No exceptions, no compromises.

Pre-Release Checklist

  • ✓Semantic HTML: <button> for actions, <a href> for navigation, landmark regions (main / nav / header / footer) — never a clickable <div>
  • ✓Keyboard: every interactive element reachable and operable via Tab alone; Esc closes modals/dropdowns and focus returns to the trigger
  • ✓Skip link: first focusable element on the page, visible on focus, jumps straight to <main>
  • ✓Focus states: visible :focus-visible ring (≥ 3:1 contrast) on every interactive element — never outline:none without a replacement
  • ✓Contrast: normal text ≥ 4.5:1, large text / non-text UI ≥ 3:1 — verified in both light and dark mode
  • ✓Color alone: never the only signal — pair every status color with an icon, label, or pattern (WCAG 1.4.1)
  • ✓Forms: every input has a visible <label for>; required fields get an asterisk + legend; autocomplete set on common fields
  • ✓Errors: role="alert" + aria-describedby on the field; an error summary with anchor links appears at the top after a failed submit
  • ✓Images: informational images get a descriptive alt; decorative images get alt="" — never omitted
  • ✓Touch targets: 44×44px minimum for every interactive element (added in WCAG 2.2 — SC 2.5.8)
  • ✓Motion: every animation respects prefers-reduced-motion: reduce; no flashing more than 3×/second (WCAG 2.3.1)
  • ✓Dynamic content: loading regions set aria-busy="true" plus a visible-to-SR "Loading…" label; modals use role="dialog" + aria-modal="true" and trap focus; submit buttons disable in-flight and re-enable in finally
  • ✓Resize & reflow: no horizontal scroll at 200% zoom or a 320px viewport (WCAG 1.4.10); font sizes in rem/em, never hard-coded px
  • ✓Screen reader: smoke-tested with VoiceOver (macOS) and NVDA (Windows) on the primary flow

  body * { visibility: hidden; }

  • ✓Include a document number and issue date on every printable record for traceability
  • ✓Never rely on hover or focus styles to convey information that must survive on paper
  • ✓Test in more than one browser's print preview — pagination breaks differ

Audit Metadata Footer

A slot composition — not a component — for drawer, modal, and page footers that surface provenance ("Generated Apr 25, 2026 · 4:47 PM · by Javier Rivera") alongside secondary export actions. Used wherever a read-only result needs a clear chain of custody.

Maps to your audit columns

ℹ
The provenance line is just your audit columns, rendered

The footer surfaces the same data your API already returns: created_by / created_at (and updated_by / updated_at once the record has been edited). A soft-deleted record (is_deleted = true) should never reach this view — filter it at the query layer, not in the UI.

Anatomy

A sticky footer strip with two zones: left = provenance line, right = action group (secondary actions first, one primary action last).

ElementSpec

Sticky behaviorThe scroll container above needs matching bottom padding to avoid overlap

Use cases

  • ✓Reports runner page — "Schedule · CSV · Excel · Export PDF"
  • ✓Order / invoice detail drawer — "Reprint · Export · Refund"
  • ✓Audit log entry detail — a "Reviewed by" line + "Export entry"
  • ✓Any read-only result viewer that records who ran it and when

Don't

  • ✕Don't use it on mutable create/edit forms — those have their own Save / Cancel footer
  • ✕Don't omit the provenance line — that's the whole point of the pattern
  • ✕Don't add more than one primary action button — keep the CTA hierarchy clean
  • ✕Don't place this footer in a non-sticky container where it would scroll off-screen

Accessibility

  • ✓The scrollable region above the sticky footer needs enough bottom padding so content is never hidden behind it
  • ✓Provenance text renders as a <p> or <span> — not an ARIA label — so screen readers read the actual content
  • ✓The provenance icon is aria-hidden="true" — decorative only, the text carries the meaning
  • ✓Use a <footer> element as the container — it gives screen reader users a landmark to jump to

  • ✓Every interactive element has a visible focus-visible ring using var(--ring)

Governed like any other instruction

ℹ
This isn't a separate process — it's the repo's cascade

The rules behind this system (design-system-checklist, design-system-consistency) are version-headed, cascade-loaded at session start, and drift-guarded by the design-system-auditor — exactly like every other governed instruction in the repo. Decisions that changed the token set are recorded as ADRs; only a citable ADR status (accepted, proposed, or deferred) may be referenced in code or commit messages — a superseded or rejected ADR means the decision no longer applies.

See the repo-governance skill for the full model — the knowledge cascade, the safety line, version headers, and the Baseline / Standard / Strict tiers a repo is held to.
