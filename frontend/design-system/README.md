# Design-system showcase

A living, versioned reference for this project's design system — scaffolded by `/setup-design-system`.

`showcase.html` is a **documentation app**, not one long scroll. A dark, always-visible sidebar groups dozens of fine-grained, single-purpose pages under a handful of sections (Overview, Brand Identity, Foundations, Design Tokens, Accessibility, Components, Patterns, Developer); a sticky topbar carries a breadcrumb, the version pill, and the light/dark toggle; and a hero-driven Home page links out to the most-used pages via a quick-start card grid. Navigation is hash-routed (`#/<page-id>`) — browser Back/Forward works as expected, and every page switch moves focus to the new heading with an `aria-live` announcement for screen-reader users. Despite the depth, it's still one self-contained file — opens directly over `file://`, no build step, no server (see [ADR-0008](../../../docs/adr/0008-showcase-dashboard.md)).

## Content model: generated vs. authored

Every page in the showcase falls into one of two buckets:

- **G — generated.** Foundations, Design Tokens, and Accessibility all render the same resolved token literals that live in the `TOKENS` marker block inside the inline `<style>` — the single source of truth is `app.css`'s `@theme` block, and `npm run showcase:build` is what keeps these pages honest. Never hand-edit the `TOKENS` block directly; edit `app.css` and re-run the build.
- **A — authored, marker-guarded.** Brand (`<!-- BRAND:START -->` … `<!-- BRAND:END -->`) and Mockups (`<!-- MOCKUPS:START -->` … `<!-- MOCKUPS:END -->`) are hand-written content specific to your product — logo, palette story, voice & tone, and the full-page mockup gallery link. `showcase-build.mjs` only ever touches the `TOKENS` block; it is guaranteed to leave every `A` block untouched, so these sections are safe to customize freely without a future rebuild clobbering your work.

Every other page (Components, Patterns, the rest of Developer) is plain hand-authored HTML documenting a convention — it isn't mechanically regenerated, but it also isn't marker-guarded, since nothing in the toolchain writes to it.

## Files

`showcase.html` is **self-contained** — opens directly in a browser, no build needed to view. It's a single HTML file with an inline `<style>` block: every token is a resolved literal (hex/oklch), there's no `app.css` link and no Tailwind import, so it renders correctly offline / over `file://` with zero build step.

| File | What it is |
| --- | --- |
| `showcase.html` | The showcase page itself. **Foundations / Design Tokens / Accessibility** render the `/* TOKENS:START */` … `/* TOKENS:END */` block (CSS comments, since they live inside the inline `<style>` block, where an HTML comment would break the CSS parse) — a resolved `:root` / `.dark` block generated from `app.css`'s `@theme` block. This is the **G** content — never hand-edit it. **Brand** (`<!-- BRAND:START -->` … `<!-- BRAND:END -->`) and **Mockups** (`<!-- MOCKUPS:START -->` … `<!-- MOCKUPS:END -->`) are HTML comments in the body — the **A** content, hand-authored; customize them freely. |
| `showcase-build.mjs` | Node script, built-ins only (no npm dependencies, no Tailwind CLI invocation). Parses `@theme` + `.dark`, resolves every token to a literal value, rewrites the `TOKENS` block in place inside `showcase.html`, and emits a sibling `tokens.json`. Emits no compiled CSS artifact — there is no `app.css` for the showcase itself. |
| `tokens.json` | Generated by `showcase-build.mjs` alongside the `TOKENS` block — a flat, deterministic `[{ name, light, dark }]` array in `app.css`'s `:root` source order. A machine-readable export of the same resolved token set for any tooling that shouldn't have to parse HTML/CSS. Committed, like the `TOKENS` block. |
| `mockups/` | Full-page, standalone HTML examples (e.g. `mockups/dashboard.html`) — see [Mockups](#mockups) below. |

## Open it

Just open the file directly in a browser — no server, no build needed:

```
# Windows
start design-system/showcase.html

# macOS
open design-system/showcase.html

# Linux
xdg-open design-system/showcase.html
```

Or drag `showcase.html` into a browser tab. It's fully self-contained (inline styles, resolved token values), so it renders correctly over `file://` with nothing to compile first.

## Rebuild after changing tokens

Whenever you edit the `@theme { … }` block in your app's CSS (colors, type scale, radius, shadow, motion, etc.), re-sync the Foundations `:root` / `.dark` token block:

```bash
npm run showcase:build
```

This rewrites the text between the `TOKENS` markers in `showcase.html` and regenerates the sibling `tokens.json` — it does not compile or emit any project CSS.

This is wired into `package.json` by `/setup-design-system`:

```json
{
  "scripts": {
    "showcase:build": "node design-system/showcase-build.mjs"
  }
}
```

**The regenerated `TOKENS` block IS committed** — and so is the regenerated `tokens.json`. Both are the living, versioned record of the token system — reviewers can see exactly what changed in a token PR by reading the diff of `showcase.html` and `tokens.json`, the same way they'd read a diff of `app.css`.

The `BRAND` and `MOCKUPS` blocks (and a reserved `KIT` marker pair, currently unused) are never touched by the build script — edit them directly to add or adjust authored content.

## Idempotency

Running `npm run showcase:build` twice in a row against an unchanged `app.css` produces byte-identical output — token order is deterministic (@theme source order), and no timestamps are embedded. Safe to run in CI as a drift check (`git diff --exit-code design-system/showcase.html design-system/tokens.json` after a rebuild).

## Locating the source CSS

`showcase-build.mjs` resolves the source CSS by trying, in order (each relative to this `design-system/` directory): the `DESIGN_SYSTEM_SOURCE_CSS` env var (an absolute-path override) → `./app.css` → `../src/app.css` → `../src/index.css` → `../css/app.css` → `../app.css`. The first that exists wins.

**In Linearr the source is [`../src/index.css`](../src/index.css)** — the app's Tailwind entry is `src/index.css`, not `app.css`, so `../src/index.css` was added to the candidate list in `showcase-build.mjs`. No env var or symlink is needed; `npm run showcase:build` finds it automatically. The color tokens come from that file's `:root { … }` / `.dark { … }` blocks and the scale/font/radius/motion tokens from its `@theme inline { … }` block.

## Mockups

`mockups/` holds full-page, standalone HTML files — the seed examples the Patterns pages link out to (see the Dashboard pattern's `<!-- MOCKUPS:START -->` … `<!-- MOCKUPS:END -->` block). Each one:

- Is self-contained: inline `<style>` with the same resolved token literals as `showcase.html`, no `app.css` link, no Tailwind import, no font CDN, no other external assets.
- Supports light/dark via the same `.dark`-class strategy, with its own small toggle (independent of the showcase's own toggle — these files are meant to be opened on their own).
- Opens directly in a browser (`file://` or a static server) with zero build step.

`mockups/dashboard.html` is the seed: a sidebar + topbar shell, a KPI stat grid, a chart-and-breakdown zone, and a data table with toolbar and pagination — the same "Dashboard" pattern documented on the Patterns page, assembled into one real screen.

To add a new mockup: copy `mockups/dashboard.html` as a starting point, keep its token values in sync with `app.css` by hand (or copy the refreshed `:root` / `.dark` block from `showcase.html` after `npm run showcase:build`), and link to it from the relevant Patterns page inside its own `<!-- MOCKUPS:START -->` / `<!-- MOCKUPS:END -->` markers so the link survives future edits.
